# Домашняя работа № 1: рекомендательные поисковые теги

## 1. Дизайн A/B-теста

**План теста: 14 дней, 0,65% пользователей суммарно, по 0,325% в контроль и тест.** Расчёт основан на допущениях ниже. Перед запуском нужно проверить их по логам.

### Метрика и допущения

Пользователя стабильно распределяем хешем ID в контроль или тест, 50/50. Контроль видит текущие теги; тест - рекомендательные на подходящих запросах. Список подходящих запросов и доступность показа фиксируем до эксперимента одинаково для обеих групп.

Основная метрика - отношение суммарных кликов по тегам к суммарному числу поисков с показом тегов **на подходящих запросах**. Считаем её на выбранном сегменте, потому что именно на нём меняются теги. Общий CTR тегов по всем запросам считаем дополнительно.

Рабочие допущения:

- Подходящие запросы составляют 20% поисков с тегами. Принимаем такую долю для расчёта, поскольку логов в задании нет.
- CTR именно этого сегмента равен 3%, хотим обнаружить рост с 3% до 3,3% (+0,3 п.п., или +10% относительно).
- DAU = 5 млн, 4 поиска на пользователя в день, доля показов тегов = 60%; показатели стабильны и применимы к случайно выбранной аудитории.
- В расчёте бинарной метрики на один поиск учитываем факт хотя бы одного клика по тегу. Если логирование допускает несколько учитываемых кликов на поиск, мощность рассчитываем по эмпирической дисперсии отношения сумм.
- Проверка двусторонняя, α = 0,05; мощность = 0,8. Один основной критерий, без досрочной остановки по значимости.

### Размер выборки

Для независимых поисков число наблюдений на одну группу:

$$
n = \frac{\left[z_{1-\alpha/2}\sqrt{2\bar p(1-\bar p)} + z_{1-\beta}\sqrt{p_0(1-p_0)+p_1(1-p_1)}\right]^2}{(p_1-p_0)^2}.
$$

Здесь p₀ = 0,03; p₁ = 0,033; p̄ = 0,0315; z₀․₉₇₅ ≈ 1,96; z₀․₈ ≈ 0,842. Получаем **около 53,2 тыс. независимых поисков на группу**.

Единица рандомизации - пользователь: поиски одного пользователя зависимы. Для предварительного расчёта принимаем коэффициент увеличения дисперсии **DE = 2**, то есть около **106,4 тыс. поисков на группу**. Значение DE не следует из условия и не гарантирует мощность без проверки на логах. Оно зависит от повторных визитов, разброса числа поисков и внутрипользовательской корреляции.

Число подходящих поисков с тегами в сутки на всём трафике:

$$
V = 5\,000\,000 \times 4 \times 0{,}60 \times 0{,}20 = 2\,400\,000.
$$

Пусть f - общая доля пользователей в двух группах, D - длительность. Тогда ожидаемое число подходящих поисков на группу равно V × D × f / 2. При D = 14:

$$
f = \frac{2 \times 106\,400}{2\,400\,000 \times 14} \approx 0{,}00634.
$$

Округляем вверх до **0,65%**. За 14 дней ожидаем **109 200 подходящих поисков на группу**. При DE = 2 это примерно 54 600 независимых наблюдений на группу.

| Параметр | Итог |
|---|---:|
| Длительность | 14 полных дней |
| Доля пользователей в эксперименте | 0,65% |
| Контроль / тест | 0,325% / 0,325% |
| Активных пользователей в сутки на группу | около 16 250 |
| Подходящих поисков с тегами на группу за тест | около 109 200 |

Число уникальных пользователей за 14 дней нельзя определить из DAU без данных о возвращаемости. Изменённый интерфейс видит только тестовая половина, причём только на подходящих запросах. Максимальная длительность уменьшает необходимую долю пользователей при принятой модели; точный оптимум проверяем по пользовательской дисперсии для разных длительностей.

### Проверка мощности и анализ

До запуска на исторических 14-дневных окнах имитируем пользовательскую рандомизацию, сохраняем все события каждого пользователя и моделируем прирост CTR на 0,3 п.п. Сценарий эффекта и зависимость событий задаём явно; проверяем мощность и при альтернативных сценариях. По симуляциям подбираем минимальную долю с мощностью ≥80%; на A/A оцениваем частоту ложных срабатываний около 5%. Пересчитываем план по фактическим CTR и покрытию.

Если доля подходящих запросов или DE окажутся другими, пересчитаем долю трафика:

$$
f_{new} \approx 0{,}00634 \times \frac{0{,}20}{s} \times \frac{DE_{fact}}{2},
$$

где s - фактическая доля подходящих поисков среди поисков с тегами, а DE оценивается для выбранной длительности. Например, при s = 10% и DE = 2 требуется около 1,27% пользователей.

Сравниваем отношение сумм кликов и показов; доверительный интервал строим бутстрэпом пользователей или дельта-методом с кластеризацией по пользователю. Не считаем поиски независимыми и не заменяем отношение сумм средним пользовательских CTR. Проверяем SRM и корректность логирования. Основной результат читаем один раз после 14 дней.

Дополнительные метрики: CTR по всем запросам, поиски и клики на пользователя, конверсия пользователя в заказ из поиска, доля поисков без товарных кликов, задержка ответа. Рост CTR не служит основанием для внедрения при ухудшении покупательского результата. Допустимые ухудшения защитных метрик фиксируем заранее; мощность по ним проверяем отдельно.

**Если требуется основная метрика по всем поискам с тегами:** при покрытии 20% и эффекте только в подходящем сегменте общий CTR вырастет приблизительно с 3% до 3,06% (+2% относительно). Для обнаружения этого эффекта при тех же упрощающих допущениях потребуется около 1,28 млн эффективных поисков на группу, или около **3,05% пользователей суммарно за 14 дней при DE = 2**. План 0,65% относится к заранее выбранному подходящему сегменту. Точный расчёт общего CTR также требует пользовательских логов, поскольку новая функция может менять число следующих поисков.

## 2. Правила отбора запросов

Используем последние 28 дней логов. Нормализуем регистр, пробелы и согласованные варианты написания. Переход - следующий вручную введённый запрос в той же сессии в пределах 10 минут. Переходы по текущим тегам исключаем из этого сигнала, чтобы уменьшить влияние существующего интерфейса. Каждый пользователь даёт не более одного наблюдения на пару запросов в сутки.

Тип товара определяем на одном фиксированном уровне каталога: «красное платье» и «льняное платье» - один тип; «ножи» и «вилки» - разные. Классификатор типов и правило определения конкретного товарного запроса проверяем на размеченной выборке.

| Условие | Проверяемая метрика и стартовый порог |
|---|---|
| Достаточно данных | ≥1 000 уникальных пользователей с исходным запросом и ≥300 с последующим запросом за 28 дней |
| Нет одного доминирующего типа товара | По товарным кликам после исходного запроса: доля крупнейшего типа ≤60%; минимум три типа имеют долю ≥10% каждый. Для этого сигнала требуется ≥300 пользователей с товарными кликами |
| Есть переходы к конкретным товарам | Среди пользователей с последующим запросом ≥40% переходят к конкретному типу товара; в таких переходах представлены ≥3 типа, каждый у ≥20 пользователей. Уточнения свойств одного типа не считаются разными товарами |
| Модель готова к показу | После удаления дублей ≥3 релевантных конкретных типа товара с доступными товарами; кандидаты проходят порог score, выбранный по независимой разметке |

Запрос отбираем, если выполнены все условия. Для недостаточно частотных запросов и неоднозначных случаев сохраняем текущие теги. Часть подходящих запросов эти правила пропустят. Для первого теста важнее отобрать запросы, в которых мы уверены.

### Проверка правил до теста

1. **Разметка.** Два независимых оценщика по единой инструкции определяют, полезнее ли для запроса выбор разных типов товаров, чем уточнение одного типа; разногласия разбираем. Проверяем страты по частоте и категориям, результаты взвешиваем по поисковому трафику.
2. **Настройка и отложенная проверка.** Пороги подбираем на обучающем периоде, затем проверяем на следующей отдельной неделе и независимой разметке. Цель - точность отбора ≥80%; показываем также доверительный интервал, покрытие и ошибки. Пороги не подбираем по результатам A/B-теста.
3. **Качество модели.** Выбираем порог score с целевой долей релевантных тегов ≥90% среди реально показываемых top-k, k ≤10. Если модель выдаёт меньше десяти тегов, знаменатель - фактическое число показанных кандидатов. Проверяем дубли, наличие товаров и распределение по категориям.
4. **Покрытие и базовая метрика.** Считаем долю подходящих запросов по числу поисков с тегами, а не по числу уникальных текстов. Проверяем её устойчивость по дням, устройствам и категориям, измеряем CTR сегмента и обновляем расчёт выборки.
5. **Техническая проверка.** В теневом режиме проверяем доступность кандидатов и задержку; на A/A - рандомизацию, SRM и сбор событий. Перед тестом фиксируем список запросов, версию модели, пороги и план анализа.

Офлайн-проверка подтверждает применимость правил и качество тегов. Причинный эффект на CTR и покупательский результат устанавливает только эксперимент.
